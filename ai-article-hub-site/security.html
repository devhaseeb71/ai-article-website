Security

What this site does to protect itself, and how to report a problem.

Reporting a vulnerability

This is a static site. There is no server, no database and no account system, so the realistic risks are limited to content injected into a page, a compromised build dependency, and misconfigured hosting headers.

If you find a genuine problem, please report it privately to security@example.org rather than opening a public issue. Include the page URL, what you observed, and how to reproduce it.

Machine-readable details, following RFC 9116, are at .well-known/security.txt.

No dependencies

There are no runtime and no build dependencies. Nothing third-party can be compromised to reach this site, and there is no lockfile to audit. The Markdown renderer is part of this project, released under the same CC0 licence as the articles.

Articles cannot inject code

Every character of article text is escaped before any formatting is applied, so a <script> tag or an onerror attribute written in an article renders as visible text. Link targets are limited to http, https and mailto; anything else is left as inert text.

Strict Content-Security-Policy

The site serves a policy that permits resources only from this origin, and nothing else:

default-src 'self';
base-uri 'self';
object-src 'none';
frame-ancestors 'none';
frame-src 'none';
child-src 'none';
form-action 'self';
script-src 'self';
script-src-attr 'none';
style-src 'self';
img-src 'self';
font-src 'self';
connect-src 'self';
media-src 'self';
manifest-src 'self';
worker-src 'self';
upgrade-insecure-requests

There is no inline script, no inline event handler, no inline style attribute, no plugin and no framing. The practical effect is that even a hypothetical content-injection bug has no way to execute code or phone home.

Because the policy forbids inline styles, all styling lives in one stylesheet. The reading-progress bar is a native <progress> element rather than a div with a percentage written into its style attribute.

Response headers

  • X-Content-Type-Options: nosniff — no MIME sniffing.
  • X-Frame-Options: DENY — this site cannot be framed, which blocks clickjacking.
  • Referrer-Policy: strict-origin-when-cross-origin — referrers are not leaked to third parties.
  • Permissions-Policy — camera, microphone, geolocation and the rest are disabled.
  • Cross-Origin-Opener-Policy and Cross-Origin-Resource-Policy — windows and files are not shared with other origins.
  • Strict-Transport-Security — enforced when the site is served over HTTPS.

No tracking

There are no analytics, no cookies, no advertising, no fonts or scripts loaded from other origins, and no third-party embeds. Reading this page involves no network requests beyond the files needed to display it.

What depends on the host

The build writes ready-to-serve configuration for common hosts: _headers for Netlify and Cloudflare Pages, vercel.json for Vercel, .htaccess for Apache, and security-headers.nginx.conf for nginx. Serving over HTTPS and keeping the web server patched are the operator's responsibility, not something the build can enforce.

The full policy, the deployment options and the verification steps are documented in SECURITY.md in the project source.
