AI in Software Development — Copilots, Code Agents and the Craft

AI assistance genuinely changes what software development feels like. It also introduces a review problem nobody solved and a way of producing code faster than anyone can read it. Both are worth understanding.

2024-04-15• Applications• 1,212 words• CC0 1.0 public domain

Software is where AI assistance has spread fastest, for three reasons: the tasks are text-shaped, the work is already digital, and — crucially — there is a verifier. Code either works or it does not.

That combination makes development the leading indicator for the rest of the economy, and the place to study what AI assistance does to a profession in real time.

What actually works

Autocomplete and inline suggestions are the most successful form of AI assistance by a wide margin, for a reason worth stating: they are cheap, fast, interruptible and dismissable. A suggestion that is wrong costs a keystroke. A suggestion that is right saves a substantial amount of typing. The asymmetry makes the interaction comfortable, and comfort is what determines adoption.

Code explanation is the second most useful capability. Understanding code you did not write — a legacy module, an unfamiliar codebase, a generated script — is a large fraction of real engineering work, and it is a task where models are strong and the cost of an imperfect answer is low.

Boilerplate and test scaffolding absorb a surprising share of development time and are almost pure pattern completion.

Search and retrieval over your own repository is high value and underused. "Where is rate limiting applied?" is a question that takes a person ten minutes and a model seconds, provided the repository is indexed.

Migration and transformation work — porting an API, changing a signature across a codebase, upgrading a dependency — is well suited to the technology, because the work is mechanical, verifiable and tedious.

Review assistance catches the classes of defect a tired human misses: forgotten error handling, inconsistent naming, missing null checks, a subtle injection. It does not catch the one defect that matters, which is the wrong business logic.

What does not work

Knowing what you want. Models implement specifications well. They do not help decide what should be built, which is most of software engineering. A confident implementation of the wrong thing is worse than no implementation, because it looks finished.

Architectural coherence. Generated code is locally plausible and locally consistent with the surrounding style, and it will happily introduce a fourth way of doing something in a codebase that already has two. Consistency of intent across a system is a human skill that current tools do not have.

Knowing your system. A model with no access to your architecture, your operational constraints, your incident history and the reason a piece of odd-looking code exists will suggest the textbook answer, and the textbook answer will be wrong in ways that are invisible until production.

Debugging distributed systems. The bugs that cost the most — a race condition, a memory leak under load, a subtly wrong deployment configuration — live in the space between components, and no amount of local code understanding reaches them.

The review problem

This is the most consequential effect and the least discussed.

When code production speeds up and review capacity does not, the ratio changes. Code accumulates in the review queue faster than it can be examined, so reviewers approve more per hour and examine less of each submission. This is a predictable consequence of incentives, not a failure of character, and it is how most systems that introduce automation into a review-dependent process degrade.

The dangerous property is that the errors generated by a language model are plausible-looking. They are idiomatic, well-formatted, consistent with the surrounding style, and often wrong in ways that require domain knowledge to spot. A human skimming fifty lines of unfamiliar-looking code has never been in a worse position, because the surface signals that normally say "read this carefully" have all been removed.

There are effective mitigations and they are mostly process changes:

  • Test the behaviour, not the text. A test that would fail if the logic were wrong is worth more than any amount of human reading.
  • Require the author to explain intent before review, in two or three sentences, so the reviewer is checking a claim rather than reconstructing one.
  • Review the diff against a stated requirement, not in isolation.
  • Make the reviewer accountable for what merges. A process where someone owns a merged change will not accept a queue backlog.
  • Raise the bar for generated code specifically. If AI wrote it, the author has not yet demonstrated they understand it. Requiring the author to be able to explain every line is a low-cost, high-yield rule.
  • Keep automated security and correctness checks in the pipeline, where they are cheap and constant.

What happens to the craft

The honest answer is that the shape of the work changes rather than disappearing.

The parts of software development that shrink are the mechanical parts: producing the second implementation of a known pattern, writing a data transformation, filling in boilerplate, recalling library APIs, writing a first draft of a test.

The parts that grow are the ones that were always the hard parts and are now the whole job: deciding what to build, understanding the system, reviewing what arrives, and being accountable for behaviour in production. A team where everyone can produce code trivially still needs someone who knows what should be produced.

The practical danger is a skills pipeline problem. Junior engineers learn by writing and debugging lots of code. If a large fraction of that writing is done for them, they produce a great deal of plausible code with much less debugging practice, and debugging is where engineering judgement comes from. This is a genuinely unresolved question and it is worth taking seriously rather than assuming it resolves itself.

Measuring whether it helped

Adoption is not productivity. A useful measurement plan looks at:

  • Cycle time from start to merge, decomposed. If total time falls but review time rises, the work moved rather than disappeared.
  • Defects escaping to production, by category, over a longer window than feels necessary. Defects that arrive later and more expensively are the signature of under-review.
  • Change failure rate and time to restore. The standard operational metrics, because they capture outcomes rather than activity.
  • Onboarding time. If new engineers ramp faster, the effect is real.
  • Time spent on unplanned maintenance, tracked for a year, not a quarter.

A useful counter-metric: the percentage of merged changes where the author could not explain a line of the diff. It is hard to automate, brutal to report, and more informative than lines of code.

A workable practice

  1. Use AI for the mechanical parts and be suspicious of it for the structural parts.
  2. Never merge code you cannot explain. If the model wrote it, you still own it.
  3. Test behaviour, and treat a passing test suite as necessary rather than sufficient.
  4. Keep the architecture in a document the model can read, so its suggestions respect your decisions instead of reinventing them.
  5. Give the model the error output, the constraints and the surrounding code. Prompt quality is still most of the quality.
  6. Measure outcomes, not lines.

The technology is genuinely good and genuinely unfinished. Both of those statements are load-bearing, and a team that believes only the first will ship a lot of code and find out about the second in production.
