Publish this site — or release your own work into the public domain

The whole publication is a static folder of HTML and Markdown. Put it on any host, any CDN, or no host at all. And because the text is CC0, you are free to fork it, translate it, cut it up, or merge it with your own work and publish that too — without asking anyone.

Step 1 — publish this site as-is

  1. Build it. With Node 18+ installed, run npm install then npm run build. Output lands in dist/. You can also run npm run zip to refresh the downloadable archives.
  2. Copy the contents of dist/ into a folder you control — or straight into any static host's upload box.
  3. Pick a host. Drag the dist/ folder onto Netlify Drop, or run npm run serve for a local preview at http://localhost:4173.
  4. Or connect a repository. Push to GitHub, then enable Pages (Settings → Pages → deploy from branch). Cloudflare Pages, Vercel, GitLab Pages, S3 + CloudFront and any static host work the same way — the output is pure files, no server runtime.
  5. Set your own base URL. Edit baseUrl in src/templates/layout.mjs so canonical URLs, the sitemap and the RSS feed point at your domain, then rebuild.

Step 2 — copy it, remix it, translate it

CC0 1.0 removes the legal friction, so the only question left is editorial. Things people commonly do with this collection:

  • Translate. Drop translated Markdown into the content/ folder, or translate the downloaded .md files and publish them under your own imprint.
  • Curate. Pull five articles into a syllabus, a newsletter issue, a course reader or a handbook. Because there are no attribution requirements, it stays simple; a credit line is still welcome.
  • Republish as a book. The Markdown and plain-text bundles feed Pandoc, Asciidoctor, MkDocs, Sphinx or Typst with no cleanup.
  • Use commercially. Sell a printed compendium, a course, a consulting library. The license permits it and asks for nothing in return.
  • Machine-readable reuse. The JSON corpus is CC0 data, usable as retrieval-augmented-generation material, a fine-tuning or evaluation set, or a translation-training source.

Step 3 — do I need to credit you?

No. CC0 waives all copyright and related rights, so there is no legal requirement to credit. It is good manners, and useful for readers, if you do. If you want to, one of these is plenty:

Step 4 — put your own work in the public domain

If you maintain a site, a handbook or a documentation set, you can dedicate it to the public domain the same way this one is dedicated.

  1. Read the CC0 deed at creativecommons.org/publicdomain/zero/1.0/. The deed is a human-readable summary; the legal code is the official text.
  2. Attach the legal code as LICENSE or LICENSE.md in the root of the work, and add SPDX-License-Identifier: CC0-1.0 to source files that benefit from machine-readable licensing.
  3. Declare it in metadata with <meta name="license" content="CC0 1.0"> and <link rel="license" href="https://creativecommons.org/publicdomain/zero/1.0/">, so scrapers and readers see it without opening the file.
  4. Say it in plain language in a LICENSE file and in the README, in the reader's language. A public domain dedication that people cannot find is a dedication nobody benefits from.
  5. Mind the exceptions. CC0 cannot waive trademark, patent, publicity or moral rights, and it does not cover third-party material you do not own. Clear any embedded assets, quotes or datasets first.

Step 5 — where people put sites like this

  • GitHub Pages — free, permanent URLs, easy history and forks. The natural home for a CC0 corpus.
  • Cloudflare Pages / Netlify / Vercel — instant deploys with previews for every change.
  • IPFS or a plain object store — content-addressed, hard to take down, good for public-domain archives.
  • Your own server — the build output is ordinary files; a 5 KB Nginx config is enough.
  • Print and PDF — the print stylesheet produces clean pages; combine the Markdown with Pandoc for a book.
  • Registries — the JSON corpus can be deposited on Zenodo or a domain-specific repository with an open license.

Step 6 — the security headers

The build already writes working configuration into dist/. Keep the file that matches your host and delete the rest, so you are not publishing a config for a server that is not there:

  • _headers — Netlify and Cloudflare Pages.
  • vercel.json — Vercel.
  • .htaccess — Apache and most shared hosts.
  • security-headers.nginx.conf — Nginx; paste the lines into your server{} block.
  • .well-known/security.txt — every host, at the path the standard requires.

All of them are generated from one file, src/lib/security.mjs, so they cannot disagree with each other or with what the checker enforces. The policy is strict: nothing loads from another origin, and there is no inline script or inline style anywhere on the site.

Before your first deploy, set baseUrl and securityContact in src/templates/layout.mjs and rebuild, so canonical links, the feed, the sitemap and security.txt point at your own domain and your own mailbox.

Read the full security policy, or SECURITY.md in the project source.
